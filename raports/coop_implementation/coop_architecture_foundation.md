# Кооперативная архитектура xray-monolith-coop для Anomaly 1.5.x

> **Статус документа:** Базовый архитектурный стандарт (Foundational Architecture Spec)  
> **Назначение:** Основной документ для реализации кооперативного режима с ALife по модели **host-authoritative / server-client**  
> **Целевая модель:** **Хост полностью контролирует мир и отправляет клиентам состояние; клиент отображает состояние и отправляет только ввод/запросы**  
> **Аудитория:** разработчики C++/Lua, Copilot/AI-ассистенты, архитекторы, QA, отладка/профилирование  
> **Проект:** `xray-monolith-coop` (форк `themrdemonized/xray-monolith`)  
> **Версия документа:** 1.1 (с интегрированными поправками amendments)

---

## 1. Цели и принципы

### 1.1 Главная цель
Реализовать стабильный кооперативный режим для Anomaly с ALife, где:
- **Хост (сервер)** является **единственным источником истины** для игрового мира.
- **Клиент** не принимает финальных геймплейных решений и не “синхронизирует логику скриптами”, а:
  - отправляет `input`/`request`,
  - получает `snapshot`/`delta`/`events`,
  - отображает мир,
  - выполняет локальное сглаживание/интерполяцию.

### 1.2 Почему именно так
Этот подход минимизирует:
- рассинхрон состояния между игроками,
- race conditions при луте/инвентаре,
- дюпы предметов,
- конфликтные скриптовые состояния,
- “магические” Lua-патчи, которые пытаются склеить сетевую логику.

### 1.3 Жёсткие архитектурные принципы (обязательные)
1. **Server-authoritative всегда**
   - Любое изменение состояния мира должно иметь **серверный источник**.
2. **Клиент не меняет мир напрямую**
   - Только запросы/ввод, без прямого authoritative изменения.
3. **Синхронизируем состояние и события, а не Lua-вызовы**
   - Lua — слой реакций/интерфейса/контента, а не транспорт или authoritative sync.
4. **ALife симулируется только на сервере**
   - Клиент получает только релевантный срез.
5. **Сетевой код отделён от геймплейного**
   - `transport != protocol != simulation != replication`.
6. **Верифицируемость и дебаг с первого дня**
   - Ревизии, логи решений сервера, ресинк, net-debug UI.
7. **Постепенная миграция**
   - Нельзя переписывать всё разом; MVP должен быть вертикальным срезом.
8. **Transport-agnostic Protocol и Replication**
   - Protocol/Simulation/Replication слои не зависят от конкретного transport backend.
   - Транспорт можно заменить без переписывания gameplay-логики.

## 2. Границы и исходные допущения проекта

### 2.1 Что уже есть в кодовой базе (высокоуровнево)
В проекте уже присутствуют ключевые подсистемы, на которые нужно опираться:
- `xrNetServer` (`IPureServer`, `IPureClient`) — существующий сетевой транспорт.
- `xrGame` — игровая логика (`game_sv_*`, `game_cl_*`, `Level_network*`, `Actor*`, ALife и др.).
- `xrServerEntities` — серверные сущности (`CSE_*` иерархия, ALife-объекты).
- `NET_Packet` и сетевые утилиты (`xrCore/net_utils.h`) — сериализация бинарных пакетов.
- Lua/LuaJIT-слой (gamedata/scripts + script_storage) — должен стать *реактивным* слоем.  

> Примечание: существующий транспорт на DirectPlay8 устаревший, но для LAN/host-based коопа его можно использовать на MVP-этапе.

> **Важное требование:** до прохождения `anomaly_compatibility_analysis.md` нельзя считать оценку трудоёмкости коопа с ALife в Anomaly окончательной.
> **Инвариант A-01:** Anomaly-специфика (db.actor, info_portions, single-actor квестовые скрипты, ALife job extensions) должна быть инвентаризирована отдельным документом как обязательный шаг перед планированием ALife-этапов.

### 2.2 Что **не** является целью первой архитектурной итерации
- Полная замена сетевого транспорта (например, на ENet/SteamSockets) в первой фазе.
- “Идеальная” синхронизация всех систем Anomaly/модов с первого дня.
- Детерминистическая lockstep-симуляция.
- Полная поддержка всех сторонних модпаков из коробки.

### 2.3 Что является обязательным для MVP
- Подключение нескольких клиентов к хосту.
- Авторитетная серверная обработка базовых действий:
  - перемещение (авторитетное состояние),
  - interact/use,
  - лут/подбор/дроп,
  - базовый инвентарь,
  - базовый HP/урон/смерть.
- Репликация игроков и базовых сущностей.
- Минимальный ALife online-bubble (сервер симулирует, клиенты видят срез).

## 3. Термины и определения

### 3.1 Роли
- **Host / Server / Хост** — процесс игры, принимающий соединения и симулирующий мир (authoritative).
- **Client / Клиент** — подключённый игрок, отображает мир и отправляет ввод/запросы.
- **Listen Server** — хост-игрок (игрок + сервер в одном процессе). Для MVP допустимо.
- **Dedicated Server** — отдельный headless-процесс (цель более позднего этапа).

### 3.2 Состояние
- **Authoritative state** — истинное состояние на сервере.
- **Replica state** — клиентская копия состояния, приходящая с сервера.
- **Snapshot** — полный (или большой) снимок состояния мира/набора сущностей.
- **Delta** — изменения относительно предыдущего подтверждённого состояния.

### 3.3 Репликация
- **Spawn** — создание реплики сущности на клиенте.
- **Despawn** — удаление реплики.
- **Interest management** — определение, какие сущности/события отправлять конкретному клиенту.
- **Bubble** — “пузырь” онлайн-симуляции вокруг игроков (объекты в активной зоне).

### 3.4 Игровые объекты
- **Server Entity** — серверное представление (`CSE_*`).
- **Game Object (runtime)** — объект игрового мира в `xrGame`/уровне.
- **Actor** — управляемый игроком персонаж.
- **NPC/Monster** — AI-сущности, управляемые сервером.
- **ALife Offline object** — сущность в серверной симуляции вне online-bubble.

## 4. Архитектурная модель

## 4.1 Общая схема

```text
+--------------------- HOST (Authoritative) ----------------------+
|                                                                 |
|  [Transport: IPureServer]                                       |
|         |                                                       |
|  [Coop Protocol Handlers]                                       |
|         |                                                       |
|  [Coop Server World / game_sv_coop]                             |
|      |        |         |         |        |                    |
|      |        |         |         |        +--> Quest/Flags     |
|      |        |         |         +----------> Inventory         |
|      |        |         +--------------------> Combat/Damage     |
|      |        +------------------------------> ALife + NPC AI    |
|      +---------------------------------------> Entity Lifecycle  |
|                                                                 |
|  [Replication Manager] --> snapshots/deltas/events --> clients  |
|                                                                 |
+-----------------------------------------------------------------+

+----------------------- CLIENT (Replica) ------------------------+
|                                                                 |
|  [Transport: IPureClient]                                       |
|         |                                                       |
|  [Coop Client Protocol]                                         |
|         |                                                       |
|  [Replica World / game_cl_coop]                                 |
|      |          |             |                                 |
|      |          |             +--> UI / Effects / Lua reactions |
|      |          +----------------> Interpolation               |
|      +---------------------------> Rendering/Presentation       |
|                                                                 |
|  [Input Capture] --> input/request --> host                     |
|                                                                 |
+-----------------------------------------------------------------+
```

## 4.2 Разделение ответственности

### Сервер отвечает за:
- жизненный цикл сущностей (spawn/despawn/ownership),
- ALife-симуляцию (online + offline),
- AI/NPC/монстров,
- инвентарь/контейнеры/лут,
- взаимодействия `interact/use`,
- урон/смерть/эффекты, влияющие на состояние,
- квестовые состояния (где возможно),
- репликацию состояния/событий.

### Клиент отвечает только за:
- захват ввода игрока,
- отправку запросов/команд,
- локальное отображение состояния,
- интерполяцию и визуальное сглаживание,
- UI/звук/эффекты,
- локальные косметические эффекты, не влияющие на authoritative state.

## 5. Слои системы (обязательное разделение)

## 5.1 Transport Layer (существующий `xrNetServer`)
### Цель слоя
Надёжная доставка бинарных пакетов между хостом и клиентами.

### Реализация на первом этапе
Использовать существующий:
- `IPureServer`
- `IPureClient`
- `NET_Packet`
- `MultipacketSender/Receiver`
- компрессию `NET_Compressor`

### Ограничения
- Не использовать transport API напрямую в gameplay-коде.
- Все send/receive должны идти через **кооп-протокольный слой**.

### Что добавить
- Обёртку/адаптер `CoopTransport` (тонкий слой над `IPureServer`/`IPureClient`):
  - `SendReliable(...)`
  - `SendUnreliable(...)`
  - `BroadcastReliable(...)`
  - `BroadcastUnreliable(...)`
  - трассировка (тип пакета, размер, получатель, latency markers)

> **Важно:** На MVP не переписывать транспорт. Протокол и репликация должны быть независимы от DirectPlay8, чтобы позже можно было заменить backend.

---

### Инварианты транспортного слоя

**Инвариант T-01: Транспорт временный**
> На этапах MVP / ранних фаз допускается использование текущего транспорта X-Ray (DirectPlay8 через `IPureServer`/`IPureClient`), **НО** транспорт считается **временным техническим компромиссом**, а не долгосрочной целевой платформой для коопа.

DirectPlay8 подходит для быстрого старта, но:
- устарел и deprecated;
- ограничивает переносимость (не работает нативно на Linux/Proton);
- является слабым местом для Linux/Steam Deck аудитории.

**Инвариант T-02: Нет лишних копирований на hot path**
> `CoopTransport` adapter не должен вводить лишние полные копирования буфера пакета на горячем пути (hot path), кроме неизбежных границ API.

### Transport Migration (Post-MVP / Post-Phase 2+)

Отдельный roadmap-этап: переход на современный transport backend.

#### Цель
Заменить DirectPlay8 без переписывания кооп-логики (благодаря transport-agnostic Protocol Layer).

#### Кандидаты
- **Steam GameNetworkingSockets** — приоритетный кандидат: relay/NAT traversal без пробрасывания портов, активно поддерживается
- **ENet** — альтернатива с простым UDP reliable/unreliable стеком

#### Преимущество Steam GNS
Встроенный relay устраняет проблему NAT traversal для интернет-коопа — это важно для аудитории Anomaly.

## 5.2 Protocol Layer (новый)
### Цель
Определить **контракт сообщений** между хостом и клиентом.

### Требования
- Версионирование протокола.
- Явные типы пакетов.
- Разделение на:
  - reliable (критичные),
  - unreliable (частые состояния).
- Явная сериализация/десериализация.
- Совместимость с `NET_Packet`.

### Обязательные элементы протокола
- `ProtocolVersion`
- `SessionId`
- `PlayerId`
- `WorldRevision`
- `EntityRevision`
- `TickId`
- `Ack`/`LastReceivedTick` (если нужен собственный механизм поверх транспорта)

---

## 5.3 Simulation Layer (server-only)
### Цель
Выполнять всю игровую симуляцию на хосте.

### Запрет
Клиент не должен самостоятельно решать:
- исход интеракции,
- валидность подбора предмета,
- изменение HP/смерти,
- окончательный результат выстрела (минимум — серверная верификация).

---

## 5.4 Replication Layer
### Цель
Переводить authoritative state сервера в:
- `spawn/despawn`,
- `snapshot`,
- `delta`,
- `events`.

### Обязательная функциональность
- Отбор объектов по interest management.
- Дельта-сжатие состояния.
- Репликация по ревизиям.
- Полный ресинк (full snapshot) по запросу/ошибке.

---

## 5.5 Script Bridge (C++ ↔ Lua)
### Цель
Сделать Lua расширяемым слоем контента, а не authoritative синхронизацией.

### Разрешено Lua
- UI
- эффекты
- сценарные реакции
- надстройки над событиями
- локальные косметические действия

### Запрещено Lua
- принимать authoritative сетевые решения,
- самостоятельно поддерживать “истину мира” для коопа,
- выполнять прямую P2P-синхронизацию вместо C++ протокола.

## 5.6 Core Engine Constraints (X-Ray legacy assumptions)

### Constraint C-01: Global single actor assumption

В legacy-коде X-Ray/Anomaly множество мест предполагают единственного "локального" актора:
- `g_actor` — глобальная переменная `CActor*`
- `Actor()` — глобальный доступ
- `db.actor` в Lua
- UI/квестовые системы, implicitly привязанные к одному игроку

Это становится критическим риском для **listen-server**, где в одном процессе одновременно живут:
- серверная симуляция мира;
- клиент хоста;
- (в будущем) несколько удалённых клиентов.

### Обязательная стратегия смягчения: `LocalPlayerContext / ActorContext`

Ввести абстракцию контекста игрока (целевой этап: Phase 2):

```cpp
// TODO_COOP_AUDIT_G_ACTOR_USAGE
struct CoopActorContext {
    CoopPlayerId player_id;
    u16          actor_entity_id;   // CSE_Abstract ID
    bool         is_local_player;   // true для хост-игрока на listen server
    bool         is_server_context; // true в server-authoritative code path
};
```

#### Принцип
- В **server code path** запрещено использовать `g_actor` как источник истины.
- В **client code path** `g_actor` допустим только как UI/render convenience для локального игрока.
- Все новые участки кооп-кода используют `player_id` / `actor_entity_id` вместо глобальных указателей.

## 7. Формальная модель состояния мира

## 7.1 Источник истины
**Только сервер** хранит полный authoritative state:
- ALife-граф и offline объекты
- online runtime объекты
- игроки/инвентари/квесты
- актуальные статусы мира

### Критическое правило
Любое изменение мира должно быть:
1. получено/инициировано сервером,
2. зафиксировано в серверном состоянии,
3. получить `revision`,
4. при необходимости отправлено клиентам.

---

## 7.2 Клиентская копия мира
Клиент хранит **реплику**, а не “настоящий мир”:
- часть объектов может отсутствовать (вне interest range),
- часть данных может быть агрегированной/урезанной,
- локальные значения могут быть сглажены.

### Что клиент не должен считать истинным
- наличие предмета до подтверждения сервера,
- успешность интеракции без `SV_ACTION_RESULT` / state delta,
- итоговый HP/урон без серверного апдейта.

---

## 7.3 Ревизии (обязательно)
Для упрощения дебага и ресинка вводятся независимые ревизии:

- `world_revision` — глобальное изменение мира
- `entity_revision[entity_id]` — изменения конкретной сущности
- `inventory_revision[player/entity]` — инвентарь/контейнер
- `quest_revision[player/global]` — квестовые состояния
- `alife_revision` — ALife-этап (опционально)

### Правило использования
- Каждое authoritative изменение увеличивает соответствующую ревизию.
- Пакеты снапшотов/дельт несут ревизии.
- Клиент отбрасывает заведомо устаревшие дельты.

## 8. Сетевой протокол (MVP + расширяемый каркас)

## 8.1 Категории сообщений

### 8.1.1 Client → Server (Requests/Input)
Клиент отправляет только:
- `CL_HELLO`
- `CL_INPUT_FRAME`
- `CL_INTERACT_REQ`
- `CL_USE_ITEM_REQ`
- `CL_INVENTORY_MOVE_REQ`
- `CL_WEAPON_ACTION_REQ`
- `CL_RESPAWN_REQ`
- `CL_PING`
- `CL_CHAT` (опционально)
- `CL_RESYNC_REQ` (диагностический)

### 8.1.2 Server → Client (Authoritative)
Сервер отправляет:
- `SV_WELCOME`
- `SV_PLAYER_BIND`
- `SV_FULL_SNAPSHOT`
- `SV_DELTA_SNAPSHOT`
- `SV_ENTITY_SPAWN`
- `SV_ENTITY_DESPAWN`
- `SV_EVENT`
- `SV_ACTION_RESULT`
- `SV_INVENTORY_STATE` / `SV_INVENTORY_DELTA`
- `SV_QUEST_STATE` (позже)
- `SV_PONG`
- `SV_RESYNC_BEGIN/END` (опционально)

## 8.2 Надёжность и частота (политика доставки)

### Reliable (критичные)
Использовать для:
- join/handshake
- spawn/despawn
- inventory operations
- action results
- quest state
- player bind / reconnect
- full snapshot fragments (если бьются на части)

### Unreliable / sequenced (частые)
Использовать для:
- позиция/поворот/анимация
- частые NPC updates
- aim direction
- non-critical FX events (если применимо)

> Если текущий транспорт плохо поддерживает типизацию надёжности, реализовать выбор режима на уровне обёртки и использовать существующие send flags.

---

## 8.3 Версионирование протокола (обязательно)
### Поля
- `u16 protocol_major`
- `u16 protocol_minor`
- `u32 content_hash` (опционально, для несовместимых билдов/модов)
- `u32 feature_flags`

### Поведение
- несовместимая major-версия → отказ в подключении;
- minor mismatch → допустим при обратной совместимости;
- несовпадение `content_hash` → **отказ в подключении** на ранних фазах (strict policy).

**Инвариант V-01: Строгая совместимость контента**
> На ранних фазах кооп поддерживается только при **идентичном** наборе модов/контента у всех участников сессии.
> Несовпадение `content_hash`/`modset_signature` → `JOIN_REJECT(CONTENT_MISMATCH)`.

## 8.4 Рекомендуемые структуры пакетов (MVP)

> Ниже описаны **логические** поля. Точный формат записи в `NET_Packet` определяется `coop_serialization.*`.

### `CL_INPUT_FRAME`
Назначение: отправка намерений игрока за кадр/тик.

Поля:

- `active_slot`
- `analog_move_x`, `analog_move_y` (если нужно)

Поля:

- `client_view_dir`

Сервер проверяет:

Поля:

### `CL_INVENTORY_MOVE_REQ`
Поля:

- `request_id`
- `src_container`
- `dst_container`
- `item_entity_id`
- `count` (для стаков)
- `src_slot`, `dst_slot` (если применимо)

---

### `CL_WEAPON_ACTION_REQ`
Поля:
- `player_id`
- `request_id`
- `weapon_entity_id`
- `action` (fire_start/fire_stop/reload/mode_switch)
- `client_shot_seq`
- `aim_origin`, `aim_dir`
- `weapon_state_hash` (опционально)

Поля:

Назначение: привязка игрока к actor сущности.

Поля:

Поля:
- `entity_id`
- `entity_type`

- `pos`, `dir`
- `base_state_blob` (типозависимый набор данных)

Поля:

Поля (логически):
- `snapshot_id`

- `events list`

### `SV_EVENT`
Назначение: отдельные события, не всегда удобно включать в entity state.

Поля:
- `event_id`
- `event_type`
- `server_tick`
- `source_entity_id`
- `target_entity_id` (опционально)

### `SV_ACTION_RESULT`
Назначение: ответ на конкретный клиентский запрос.

Поля:

- `server_tick`
- `optional_message_id` (для UI/логики)
- `side_effect_flags` (state_changed/inventory_changed/etc.)

## 9. Серверный тик (обязательный контракт исполнения)

## 9.1 Общий pipeline server tick
Это **основной контракт архитектуры**. Любая реализация должна следовать этому порядку.

### Шаг 1. Receive
- Считать все входящие пакеты из транспорта.
- Превратить их в структурированные сообщения протокола.
- Разложить по очередям игроков/типов сообщений.

### Шаг 2. Validate (синтаксическая + логическая валидация)
- корректность формата пакета,
- допустимые значения полей,
- актуальность `player_id`,
- защита от повторных/устаревших `request_id`,
- базовые ограничения частоты (rate limit).

### Шаг 3. Stage Inputs / Requests
- Сложить `CL_INPUT_FRAME` в буфер входа игрока.
- `CL_*_REQ` перевести в очередь запросов на обработку.

### Шаг 4. Simulate Players
- Применить input к серверным актор-сущностям.
- Выполнить валидацию движения (коллизии/скорость/состояния).

### Шаг 5. Simulate World / ALife / AI
- Обновить online NPC/монстров.
- Обновить активные объекты мира.
- Выполнить ALife-шаг (offline/online в рамках политики).
- Обработать аномалии, зоны, триггеры.

### Шаг 6. Resolve Requests / Conflicts
- Обработать интеракции, лут, использование предметов.
- Разрешить конфликты:
  - два игрока лутают один предмет,
  - двойное открытие контейнера,
  - use предмета при изменившемся состоянии.
- Зафиксировать результаты и ревизии.

### Шаг 7. Build Replication Output
Для каждого клиента:
- вычислить interest set,
- собрать спавны/деспавны,
- собрать дельты сущностей,
- добавить события,
- добавить инвентарь/квестовые дельты (если релевантно).

### Шаг 8. Send
- Отправить сформированные пакеты через transport.
- Обновить server-side метрики доставки/очередей.

### Шаг 9. Trace / Metrics
- Записать лог решений (debug mode).
- Обновить telemetry counters.

---

## 9.2 Частота тиков и тайминг
### Рекомендация
Ввести отдельные частоты:
- `server_tick_rate_hz` (основной игровой/сетевой тик): например 20–30 Гц (настраиваемо)
- `alife_tick_rate_hz` (ALife-шаг): **отдельная настройка**, может быть реже основного тика (например 5–10 Гц)
- `replication_rate_high` (игроки/NPC близко): 10–20 Гц
- `replication_rate_low` (дальние объекты): 2–5 Гц

### Принцип
Симуляция и репликация могут иметь разные частоты.

ALife-подсистема тяжелее и не обязана обновляться на той же частоте, что обработка input или сетевые heartbeat. Серверный pipeline должен корректно работать при `alife_tick_rate_hz < server_tick_rate_hz`.

## 10. ALife в кооперативе (ядро сложности)

## 10.1 Базовый принцип
**ALife полностью серверный.** Клиент не симулирует ALife, а только отображает online-срез.

## 10.2 Модель `offline + online bubble`
### Offline ALife (server-only)
Сущности вне зон интереса игроков:
- существуют в ALife,
- обновляются в упрощённой серверной модели,
- не реплицируются клиентам.

### Online ALife (replicated)
Сущности в активной зоне хотя бы одного игрока:
- активируются в runtime,
- получают сетевую репликацию,
- обновляются сервером более детально.

### Shared Bubble
Если несколько игроков рядом:
- сущность одна (серверная),
- состояние одно (authoritative),
- всем клиентам отправляется одинаковая authoritative реплика.

---

## 10.3 Политика активации/деактивации ALife-объектов
### Условия перевода Offline → Online
- объект попал в interest/bubble любого игрока,
- объект критически важен (квест/бой/триггер),
- объект взаимодействует с online сущностью.

### Условия перевода Online → Offline
- объект вышел из всех bubble,
- не участвует в активном бою/интеракции,
- нет “подвешенных” запросов/состояний.

### Требование
Переходы должны быть **атомарными** относительно server tick (не в середине применения дельт).

---

## 10.4 ALife и квесты
### На ранних этапах
- Не пытаться синхронизировать все сюжетные ветки полностью.
- Определить ограниченный набор **server-authoritative quest flags**, которые реально влияют на мир/кооп.

### На зрелом этапе
- Ввести:
  - `global_quest_state` (общий мир),
  - `per-player quest state` (персональные состояния),
  - политику разрешения конфликтов при совместном выполнении.

## 11. Жизненный цикл сущностей (Entity Lifecycle)

## 11.1 Источник сущностей
Сервер создаёт/уничтожает сетевые сущности на основании:
- ALife и runtime world,
- действий игроков,
- триггеров/скриптов,
- боевых событий.

## 11.2 Сетевой жизненный цикл
```text
Server creates entity
 -> assign CoopEntityNetId
 -> register replication component/state
 -> emit SV_ENTITY_SPAWN to interested clients
 -> include in delta snapshots
 -> on destroy/out-of-interest emit SV_ENTITY_DESPAWN
```

## 11.3 Ownership
### Правило (MVP)
- **Сервер владеет всеми сущностями**.
- У клиента нет authoritative ownership.
- Локальная предикция игрока не означает ownership сущности.

### Расширение (позже, если нужно)
Можно ввести “input ownership” для акторов (клиент отправляет управление своим actor), но не “state ownership”.

---

## 11.4 Репликационные компоненты состояния (рекомендуемая модель)
Чтобы не сериализовать каждый класс вручную целиком, логически выделить компоненты:

- `TransformReplica`
  - pos, rot, velocity (при необходимости)
- `VitalReplica`
  - hp, stamina, bleeding, alive/dead flags
- `AnimReplica`
  - movement state, action state, overlay flags
- `InventoryReplica`
  - revisions + данные (для владельца/открытых контейнеров)
- `CombatReplica`
  - active weapon, reload state, fire mode
- `AIReplica`
  - high-level state (idle/combat/search/flee), target id (если нужно)
- `InteractionReplica`
  - door/container/open/locked/active states
- `QuestRelevantReplica`
  - минимальные флаги, влияющие на мир/UI

## 12. Игроки и несколько акторов (ключевая архитектурная задача)

## 12.1 Проблема
SP-логика исторически ориентирована на одного `Actor`. В коопе нужно поддержать несколько игроков/акторов.

## 12.2 Рекомендуемая модель
Ввести явные сущности управления:

### `CoopPlayerSession`
Содержит:
- `player_id`
- `client_id`
- `actor_entity_id`
- состояние подключения
- профиль игрока
- pending requests
- inventory/quest revisions
- reconnect token/state

### `PlayerActorBinding`
Отдельная логика привязки:
- spawn actor для игрока
- rebinding при reconnect
- death/respawn
- level transition (если будет)

### Требование к новому кооп-коду

### Стратегия миграции

## 13. Инвентарь, контейнеры, лут (приоритет №1)

## 13.1 Почему это критично
Именно здесь чаще всего возникают:
- дюпы,
- пропажа предметов,
- race conditions,
- desync UI vs world.

## 13.2 Правила (обязательные)
1. **Инвентарь authoritative на сервере**
2. Клиент отправляет только `CL_INVENTORY_MOVE_REQ` / `CL_USE_ITEM_REQ`
3. Сервер подтверждает результат через:
   - `SV_ACTION_RESULT`
   - `SV_INVENTORY_DELTA`
   - при необходимости `SV_ENTITY_DESPAWN` (если предмет поднят из мира)

## 13.3 Обработка конфликтов (пример)
Сценарий: два игрока одновременно подбирают один предмет.
- Оба отправляют `CL_INTERACT_REQ` / `pickup`.
- Сервер принимает оба запроса, но:
  - первым по tick/order обрабатывает успешный,
  - второму возвращает `SV_ACTION_RESULT(denied_already_taken)`.
- Сервер отправляет `SV_ENTITY_DESPAWN` всем заинтересованным клиентам.

## 13.4 Контейнеры
### Требование
Контейнеры должны иметь отдельную server-side ревизию (`inventory_revision[container_id]`).

### Политика
- Открытие контейнера — `interact request`.
- Клиент получает **срез состояния контейнера** только после подтверждения.
- Любые изменения контейнера — только через сервер.

---

## 14. Interact / Use / Action Requests (приоритет №1)

## 14.1 Унифицированная модель запросов
Все действия клиента должны идти через общую схему:

1. Клиент отправляет `Request` c `request_id`.
2. Сервер валидирует.
3. Сервер применяет или отклоняет.
4. Сервер отвечает:
   - `SV_ACTION_RESULT`
   - и/или state delta / event.

## 14.2 Валидация на сервере (минимальный набор)
Для `interact`:
- расстояние до объекта,
- доступность/существование объекта,
- состояние объекта (locked/opened/destroyed),
- line-of-sight (по необходимости),
- cooldown/занятость.

Для `use item`:
- предмет есть в authoritative инвентаре игрока,
- предмет в нужном состоянии,
- действие допустимо текущим состоянием игрока.

---

## 15. Перемещение и состояние акторов

## 15.1 Модель управления
Клиент отправляет `CL_INPUT_FRAME`; сервер симулирует и присылает authoritative transform.

## 15.2 Клиентское отображение
### Для собственного игрока
- На MVP можно использовать минимальную локальную предикцию или вообще без неё (будет более “тяжёлое” управление).
- Рекомендуется позже ввести предикцию + reconciliation.

### Для других игроков и NPC
- Только интерполяция/экстраполяция в малых пределах.
- При сильном расхождении — hard snap.

## 15.3 Ограничения анти-чит/валидации (даже для коопа)
Сервер должен ограничивать:
- скорость движения,
- невозможные телепорты,
- недопустимые состояния (например, действие в оглушении, если это запрещено),
- spam input rate.

---

## 16. Бой, оружие, урон, смерть

## 16.1 Принцип
Авторитетный бой должен рассчитываться на сервере (или минимум — серверная верификация хитов).

## 16.2 Этапность внедрения
### MVP (упрощённо)
- Клиент шлёт `CL_WEAPON_ACTION_REQ`.
- Сервер проверяет возможность выстрела/состояние оружия.
- Сервер определяет результат (или верифицирует хитскан).
- Сервер отправляет `SV_EVENT` + `SV_DELTA_SNAPSHOT` (HP, состояния и т.п.).

### Этап 2+
- Более точная серверная баллистика,
- репликация projectile/event streams,
- разграничение визуальных/authoritative эффектов.

## 16.3 Смерть/нокаут
Смерть — только серверное решение:
- сервер выставляет `alive=false`,
- обновляет ревизии,
- спавнит труп/лут (если применимо),
- отправляет `SV_EVENT(death)` и state deltas.

## 17. Клиентский “только отображение” режим — что это означает на практике

## 17.1 Что клиент может делать локально
- интерполяция позиций,
- локальные анимации переходов,
- UI-подсветка потенциального interact target,
- локальные звуки/эффекты, не влияющие на состояние.

## 17.2 Что клиент не имеет права фиксировать
- успешность открытия/подбора/использования,
- изменение инвентаря,
- изменение HP/смерти,
- спавн/деспавн объектов.

## 17.3 UX-компенсации (чтобы не было “лагового” ощущения)
- локальное отображение “ожидания” действия (pending interact),
- прогресс/иконка pending request,
- предиктивная анимация кнопки/use (откат при deny),
- быстрые `SV_ACTION_RESULT`.

## 18. Lua-слой: новая роль и интеграция

## 18.1 Главный принцип
Lua не является сетевым фундаментом коопа.

## 18.2 Разрешённая роль Lua
- UI и HUD-логика,
- визуальные и звуковые реакции,
- контентные сценарии,
- расширения/моддинг,
- обработка серверных событий через C++ bridge.

## 18.3 Обязательный C++ → Lua bridge
Ввести явные события (примерный набор):
- `on_coop_connected(player_id, session_info)`
- `on_coop_disconnected(reason)`
- `on_coop_action_result(request_id, result_code, payload)`
- `on_coop_inventory_changed(owner_id, revision)`
- `on_coop_entity_event(event_type, entity_id, payload)`
- `on_coop_quest_state_changed(scope, revision)`

## 18.4 Чего нельзя делать через Lua
- authoritative синхронизацию позиции/инвентаря/логаики взаимодействий,
- P2P-мосты между клиентами,
- дублирование authoritative state поверх C++ netcode.

## 19. Interest Management (критично для производительности и трафика)

## 19.1 Зачем нужен
Без фильтра интереса:
- трафик растёт взрывно,
- CPU сервера забивается сериализацией,
- клиенты получают лишние данные,
- ALife online-часть разрастается без контроля.

## 19.2 Базовые критерии интереса (MVP)
Для клиента считать релевантными:
1. Его actor и всё жёстко связанное с ним.
2. Игроки/NPC/монстры в радиусе `R_near`.
3. Предметы/контейнеры в радиусе `R_items`.
4. Объекты, с которыми клиент взаимодействует прямо сейчас.
5. Критические квестовые/сценарные объекты (если влияют на UI/процесс).

## 19.3 Уровни детализации репликации (LOD)
### High detail
- близкие игроки/NPC в бою,
- полный transform + action state + vital state

### Medium detail
- средняя дистанция,
- реже обновления, укрупнённые состояния

### Low detail
- дальние, но ещё релевантные объекты,
- сильно урезанный набор полей и редкая частота

## 19.4 Политика hysteresis
Чтобы избежать постоянного spawn/despawn на границе радиуса:
- использовать `R_enter` и `R_exit` (например, 50м / 60м),
- объект удалять только после устойчивого выхода за `R_exit`.

## 20. Snapshot / Delta стратегия

## 20.1 Full Snapshot
Используется:
- при входе клиента в сессию,
- при reconnect,
- при критическом рассинхроне,
- при диагностическом `CL_RESYNC_REQ`.

### Требования
- фрагментация больших снапшотов,
- сборка на клиенте с проверкой целостности,
- блокировка применения дельт до завершения full snapshot (или буферизация).

### Контракт фрагментации (обязательные поля фрагмента)
```
snapshot_transfer_id   - идентификатор передачи
snapshot_revision      - ревизия снапшота
fragment_index         - индекс фрагмента (0-based)
fragment_count         - всего фрагментов
fragment_payload_size  - размер payload в байтах
payload                - данные фрагмента
checksum               - контрольная сумма (на фрагмент или на весь снапшот)
```

### Правила сборки
1. Клиент **не применяет** partial snapshot.
2. Snapshot применяется только после получения **всех фрагментов** и проверки целостности.
3. При таймауте сборки — discard partial snapshot и запрос повторной передачи.
4. Пока full snapshot не применён, клиент остаётся в `Syncing / SnapshotLoading`.

> `TODO_COOP_SNAPSHOT_FRAGMENTATION_LIMITS`: определить MAX_SNAPSHOT_FRAGMENT_SIZE, SNAPSHOT_ASSEMBLY_TIMEOUT_MS, MAX_INFLIGHT_SNAPSHOT_TRANSFERS.

## 20.2 Delta Snapshot
Основной рабочий режим:
- отправлять только изменившиеся поля,
- по возможности группировать изменения по сущностям,
- прикладывать `base_revision`.

## 20.3 Политика fallback
Если клиент пропустил базовую ревизию/снапшот:
- сервер помечает клиента “needs_resync”
- отправляет full snapshot.

## 21. Сохранения, сессии и переподключение

## 21.1 Истина сейва
**Серверный сейв** — единственный источник сохранённого мира.

Сейв содержит:
- глобальное состояние мира/ALife,
- состояние сущностей,
- per-player state:
  - инвентарь,
  - позиция,
  - статы,
  - персональные квесты/флаги (если есть).

## 21.2 Reconnect
При переподключении:
1. клиент проходит `CL_HELLO` / handshake,
2. сервер восстанавливает `CoopPlayerSession`,
3. отправляет `SV_PLAYER_BIND`,
4. отправляет `SV_FULL_SNAPSHOT`,
5. после применения — переходит на `SV_DELTA_SNAPSHOT`.

## 21.3 Рекомендация
Ввести `reconnect_token` (эпhemeral в рамках сессии) для безопасного повторного подключения того же игрока.

## 22. Ошибки, отказоустойчивость и ресинк

## 22.1 Типы ошибок
- сетевые (доставка/таймаут/дисконнект),
- протокольные (невалидный пакет),
- логические (невозможное действие),
- рассинхрон (ревизии не совпали),
- внутренние ошибки сериализации/применения.

## 22.2 Политика обработки
### Невалидный запрос клиента
- не падать,
- логировать,
- отклонить с `SV_ACTION_RESULT(denied_invalid_request)`.

### Рассинхрон ревизий
- пометить клиента `needs_resync`,
- отправить `SV_RESYNC_BEGIN` (опционально),
- отправить full snapshot,
- `SV_RESYNC_END`.

### Критическая ошибка на сервере
- лог с подробным контекстом (tick, player_id, request_id, entity_id),
- по возможности graceful disconnect виновного клиента, а не краш всей сессии.

## 23. Потоки, производительность и безопасность изменений

## 23.1 Потоковая модель (рекомендация для MVP)
Для минимизации сложности:
- authoritative симуляция и обработка gameplay — в **основном серверном потоке** (или потоке game logic).
- сетевой приём может быть buffered/queued, но применение — в server tick.

## 23.2 Что не делать на MVP
- Параллельное изменение одних и тех же world state структур без строгой синхронизации.
- “Случайные” фоновые потоки, меняющие ALife/инвентари.

## 23.3 Профилирование
Добавить counters:
- длительность шагов server tick,
- время сериализации снапшотов/дельт,
- размер пакетов по типам,
- число реплицируемых сущностей на клиента.

## 28. Риски и меры снижения

## 28.1 Риск: Слишком ранняя попытка синхронизировать “всё”
**Снижение:**
- строгий этапный roadmap,
- сначала MVP вертикальный срез.

## 28.2 Риск: Lua продолжит менять authoritative state
**Снижение:**
- feature flag для отключения конфликтных Lua net patches,
- C++ hooks и bridge events вместо прямых скриптовых sync-костылей.

## 28.3 Риск: Перегрузка сети из-за ALife
**Снижение:**
- interest management,
- LOD репликация,
- offline/online bubble.

## 28.4 Риск: Хаос в коде из-за смешивания слоёв
**Снижение:**
- отдельные файлы подсистем,
- контракт server tick,
- protocol layer как единственная точка формата сообщений.

## 28.5 Риск: Отсутствие Host Migration
**Описание:** если хост (listen server) отключается — сессия завершается полностью.
**Статус:** host migration **не поддерживается** и не планируется в ранних фазах. Это осознанное ограничение.
**Снижение:** явное информирование игроков; рассмотреть в будущем после стабилизации dedicated server.

## 28.6 Риск: DirectPlay8 — устаревший транспорт
**Описание:** DirectPlay8 deprecated, не работает нативно на Linux/Proton, ограничена отладка на современных системах.
**Снижение:**
- transport-agnostic Protocol Layer с первого дня,
- `CoopTransport` adapter как единственная точка смены транспорта,
- явный Roadmap Этап 7 (Transport Migration).

## 29. Минимальные acceptance criteria (архитектурная готовность)

Система считается архитектурно реализуемой/жизнеспособной, если выполняются следующие условия:

1. **Join/Bind**
   - Клиент подключается и получает корректный `player_id`, bind к actor.

2. **Authoritative transform**
   - Перемещение других игроков отображается только через серверные апдейты.

3. **Authoritative interact**
   - Любое взаимодействие (`interact/use`) проходит через запрос и серверный результат.

4. **Authoritative inventory**
   - Нет дюпов/гонок при одновременном луте одного предмета.

5. **Server-only ALife (basic)**
   - Онлайн NPC/монстры синхронны для двух клиентов в одной зоне.

6. **Resync**
   - Клиент может получить full snapshot после десинка без краша сессии.

7. **Debug trace**
   - По логам можно восстановить цепочку: `request -> validation -> apply -> replicate`.

## 32. Инструкции для Copilot (как реализовывать по этому документу)

### 32.1 При создании новой функциональности Copilot должен:
1. Сначала определить:
   - серверная часть,
   - клиентская часть,
   - протокольные сообщения,
   - сериализацию.
2. Реализовать **server-authoritative путь**.
3. Добавить trace/logging.
4. Добавить обработку ошибок/deny.
5. Только затем добавлять Lua/UI hooks.

### 32.2 При рефакторинге существующего кода Copilot должен:
- не ломать `single` и текущие режимы MP,
- не заменять поведение глобально, если можно ввести `coop`-ветку,
- помечать места с single-actor assumptions.

### 32.3 При работе с Lua-интеграцией Copilot должен:
- использовать C++ → Lua bridge события,
- не реализовывать сетевую authoritative синхронизацию на Lua,
- не добавлять клиент-клиент обмен.

## 33. Итоговый архитектурный контракт (краткая формула)

> **Любое изменение игрового мира в кооперативе должно быть принято, проверено и применено хостом, после чего распространено клиентам через протокол снапшотов/дельт/событий. Клиент отправляет только ввод и запросы, а отображает только серверную истину.**

Это главный инвариант проекта. Все решения должны проверяться на соответствие этому правилу.

## Приложение A. Чек-лист ревью архитектурного PR
Перед merge любого PR, затрагивающего кооп-ядро, проверить:

- [ ] authoritative логика на сервере?
- [ ] протокол определён и сериализация реализована?
- [ ] есть валидация клиентского запроса?
- [ ] есть `SV_ACTION_RESULT` / state delta / event?
- [ ] есть логирование/trace?
- [ ] не используется Lua как основной sync-слой?
- [ ] нет прямого transport-вызова из gameplay логики?
- [ ] не ломаются `single` и существующие режимы?
