# Оценка архитектуры кооперативного режима

> Документ: экспертная оценка `coop_architecture_foundation.md` и `phase_1.md`  
> Дата: 2026-02-22  
> Контекст: анализ грамотности предлагаемой реализации кооп-режима для Anomaly 1.5.x на базе xray-monolith-coop

---

## Общий вердикт

**Архитектура разработана на высоком уровне.** Оба документа демонстрируют профессиональный подход к сетевому программированию, понимание специфики X-Ray движка и реальных проблем кооперативных игр. Большинство ключевых архитектурных решений верны и хорошо обоснованы.

**Оценка:**
- `coop_architecture_foundation.md`: **9/10** — исключительно грамотный документ с минимальными зонами риска
- `phase_1.md`: **9/10** — правильно определены границы MVP и сделан фокус на что действительно важно
- Совместная последовательность документов: **отлично** — правильная очерёдность (сначала фундаментальная архитектура, потом первый шаг)

## Что сделано правильно

### ✅ 1. Server-authoritative принцип соблюдён строго и последовательно

Главный принцип «хост — единственный источник истины» проведён через весь документ без исключений. Это критически важно для X-Ray:

- ALife только на сервере ✅
- Клиент отправляет только input/requests ✅  
- Инвентарь только через сервер ✅
- Урон/смерть только через сервер ✅
- Спавн/деспавн только через сервер ✅

В классических X-Ray моддерских попытках сделать кооп через Lua-синхронизацию именно нарушение этого принципа становилось причиной дюпов, дублирования смертей, рассинхрона инвентаря. Здесь этот риск полностью устранён на архитектурном уровне.

---

### ✅ 2. Правильная многоуровневая слоистость

Разделение на 5 слоёв (Transport → Protocol → Simulation → Replication → Script Bridge) — классически правильная модель для игрового сетевого движка:

```
Transport (xrNetServer) — не трогаем
  └── Protocol (coop_packet_ids, coop_serialization) — новый
        └── Simulation (game_sv_coop, server world) — новый
              └── Replication (coop_replication_mgr, interest_mgr) — новый
                    └── Script Bridge (C++→Lua events) — новый
```

Критически важно, что существующий транспорт (DirectPlay8) предлагается **переиспользовать без замены** на первом этапе — это реалистично и снижает риск провала MVP.

---

### ✅ 3. Правильная работа с ALife

Модель `offline bubble + online bubble` — единственно верный подход для Anomaly/CoC/COP. ALife — главная техническая сложность X-Ray кооп, и документ это понимает:

- Только сервер симулирует ALife ✅
- Online/offline transitions с условиями ✅
- Shared bubble для нескольких игроков ✅
- Атомарные переходы относительно server tick ✅
- Правила hysteresis (R_enter/R_exit) ✅

Особенно хорошо, что явно зафиксировано: квесты и сюжет — на более поздний этап. Это правильно — пытаться синхронизировать Anomaly ALife + квесты + инфопорции с первого дня гарантированно убьёт проект.

---

### ✅ 4. Инвентарь и conflict resolution

Один из главных источников проблем в кооп STALKER — одновременный лут. Документ правильно решает это через:

1. Сервер-authoritative инвентарь
2. Запросы `CL_INVENTORY_MOVE_REQ`
3. Ответы `SV_ACTION_RESULT`
4. `SV_INVENTORY_DELTA` после каждого изменения
5. Ревизии контейнеров

Пример с двумя игроками на одном предмете (секция 13.3) — корректен. Модель "первый успевает, второй получает `denied_already_taken`" — стандартная и правильная.

---

### ✅ 5. Система ревизий

Введение `world_revision`, `entity_revision`, `inventory_revision`, `quest_revision` — это обязательный механизм для надёжной дельта-синхронизации. Без ревизий невозможно:
- отбросить устаревшие пакеты
- восстановиться после рассинхрона
- реализовать надёжный resync

Документ правильно требует ревизии везде, где есть синхронизируемое состояние.

---

### ✅ 6. Lua — реактивный слой, не сетевой

Одно из лучших решений в документе — чёткое разграничение роли Lua:

> «Lua не является сетевым фундаментом коопа»

И перечень того, что Lua **не должен** делать (секция 18.4) — практически исчерпывающий список ошибок, которые допускают все незрелые X-Ray кооп-попытки. Явный запрет на P2P-мосты через Lua и `socket.lua` как транспорт — абсолютно правильный.

---

### ✅ 7. Серверный тик как контракт исполнения

9-шаговый server tick pipeline (Receive → Validate → Stage → Simulate Players → Simulate World → Resolve Conflicts → Build Replication → Send → Trace) — это канонический порядок для авторитетного игрового сервера. Явная фиксация этого порядка — гарантия, что в будущем не возникнет хаоса в последовательности исполнения.

---

### ✅ 8. Phase 1 правильно ограничен

`phase_1.md` демонстрирует хорошее понимание принципа "вертикальный срез":

- Только handshake + host/connect из меню ✅
- Явные out-of-scope (ALife, инвентарь, стрельба, квесты) ✅
- Acceptance criteria конкретны и верифицируемы ✅
- Минимальный stub разрешён ✅
- Конкретный Task Breakdown по подэтапам (1.A → 1.D) ✅
- Acceptance Test Plan с конкретными тест-кейсами ✅

Граница "первый успешный handshake по LAN без падения" — правильная точка завершения Phase 1.

---

### ✅ 9. Антипаттерны и риски зафиксированы явно

Список из 7 антипаттернов (секция 30) и список рисков с мерами снижения (секция 28 и 15) — это зрелый подход к документированию архитектуры. Особенно ценно, что риск "слишком ранней попытки синхронизировать всё" поставлен на первое место.

Принцип "не ломать single и MP режимы" с использованием отдельных `game_sv_coop`/`game_cl_coop` классов — правильная стратегия изоляции. Feature flags (`COOP_MODE_ENABLED`, `COOP_DEBUG_TRACE`) — стандартная практика.

## Зоны риска и замечания

### ⚠️ 1. DirectPlay 8 — главное техническое ограничение

**Проблема:** DirectPlay 8 — устаревший Windows API, который:
- официально deprecated с Vista+
- не работает на Wine/Proton (Linux-пользователи Anomaly)
- имеет ограниченные возможности настройки latency/QoS
- плохо поддаётся отладке на современных системах

**Что предлагает документ:** переиспользовать "на MVP-этапе" и сделать transport-агностичный Protocol Layer, чтобы потом можно было заменить.

**Оценка:** решение верное как стратегия, но нужно чётко понимать: если аудитория Anomaly включает Linux/Steam Deck пользователей, то замена транспорта неизбежна и должна быть в roadmap явно. Документ упоминает ENet/SteamSockets — это правильные кандидаты для замены.

**Рекомендация:** добавить в roadmap явный этап "Transport Migration" (ENet или Steam GameNetworkingSockets) с оценкой трудоёмкости.

---

### ⚠️ 2. Listen Server как основная модель — дополнительные сложности

Документ явно выбирает Listen Server (хост = игрок + сервер в одном процессе) как MVP. Это обоснованно для быстрого старта, но создаёт специфические проблемы X-Ray:

- **g_actor singleton**: в текущем коде X-Ray `CActor* g_actor` — глобальная переменная, предполагающая одного актора. На Listen Server одновременно нужен и серверный, и клиентский актор хост-игрока. Документ это упоминает (`TODO_COOP_SINGLETON_ACTOR_ASSUMPTION`), но конкретного решения не предлагает.
- **Рендер + симуляция в одном процессе**: на хосте нагрузка удваивается (рендеринг + полная серверная симуляция). Это может быть проблемой производительности на слабых ПК.

**Рекомендация:** уже в Phase 2 запланировать решение `g_actor singleton` — либо через контекст игрока, либо через абстракцию `LocalPlayerContext`.

---

### ⚠️ 3. ALife и квестовая архитектура Anomaly — недооценённая сложность

Документ правильно откладывает квесты на поздние этапы, но не полностью оценивает специфику Anomaly:

- В Anomaly квестовая система глубоко завязана на `info_portions` — глобальные флаги, которые меняют весь мир. При двух игроках возникает вопрос: info_portions глобальны или per-player?
- Множество скриптов Anomaly использует `db.actor` без проверки — они будут ломаться при двух активных акторах.
- ALife в Anomaly содержит тысячи скриптовых расширений (гулаги, джобы, смарт-террейны) — все они написаны под одного игрока.

**Рекомендация:** добавить отдельный документ `anomaly-compatibility-analysis.md` с инвентаризацией всех мест в скриптах Anomaly, которые предполагают одного актора. Это поможет оценить реальный объём работы.

---

### ⚠️ 4. Client Prediction — верное решение "отложить", но нужен plan

Документ правильно говорит: prediction — позже. Но без хотя бы минимальной локальной предикции движения управляемого персонажа кооп будет ощущаться очень "лагово" даже при пинге 20-30мс.

Базовая предикция позиции + reconciliation — это не "nice to have", это фактически обязательная часть для играбельного кооп. Стоит явно обозначить в roadmap этап "minimal client prediction" как критический для UX, а не просто "улучшение".

---

### ⚠️ 5. Размер и фрагментация Full Snapshot

Документ упоминает фрагментацию больших снапшотов, но конкретных лимитов нет. В Anomaly мир может содержать тысячи ALife-объектов. Full Snapshot при входе в сессию может быть очень большим.

**Рекомендация:** в `coop-protocol-mvp.md` явно определить:
- максимальный размер фрагмента
- порядок сборки
- таймаут на сборку полного снапшота

---

### ⚠️ 6. NAT traversal вынесен "за рамки MVP" — правильно, но нужно решение

Для пользователей без возможности проброса портов (NAT, CGNAT) LAN-only кооп не решает проблему. Документ честно это признаёт. Вариант через Steam GameNetworkingSockets (если будет миграция транспорта) даёт relay бесплатно — стоит это зафиксировать как архитектурное преимущество будущей замены транспорта.

---

### ℹ️ 7. Мелкие замечания

- **`CoopTransport` adapter**: правильная идея, но нужно убедиться, что адаптер не добавляет лишние копирования буферов — в X-Ray с его 16KB пакетами это важно для производительности.
- **`server_tick_rate` 20–30 Гц**: для Anomaly с её ALife это разумно. Но нужно подобрать значение относительно нагрузки ALife — возможно, ALife-шаг нужно выполнять реже (например, 5–10 Гц), чем основной физический тик.
- **Версионирование протокола**: документ правильно вводит `protocol_major/minor`, но не оговаривает политику `content_hash` для модов. В Anomaly-экосистеме несовместимость модов — серьёзная проблема. Рекомендуется явно заявить политику: "кооп работает только при идентичном наборе модов".
- **`coop_debug_trace.*` отдельным файлом** — правильно выделить, это поможет отключать в релиз-билдах.

## Что может не хватать

### 1. Level Transition (смена уровней в коопе)

Документ не рассматривает переход между уровнями (сюжетные переходы). В Anomaly это происходит через `M_CHANGE_LEVEL`. В коопе нужна синхронизация: все клиенты должны перейти на новый уровень одновременно. Это нетривиальная задача, которую стоит хотя бы упомянуть в roadmap.

### 2. Host Migration

Если хост отключается — сессия умирает. Для консистентного коопа желательна передача роли хоста. Документ не упоминает эту задачу даже как "later". Стоит добавить хотя бы как известный риск.

### 3. Anti-cheat в кооп

В документе упоминается валидация movement и rate limiting. Но в Anomaly-коопе (между друзьями) строгий анти-чит не критичен — и документ правильно не тратит на это время. Достаточно базовой серверной валидации.

## Сравнение с известными подходами в X-Ray моддинге

| Подход | Проблема | Как решает данная архитектура |
|--------|---------|-------------------------------|
| Lua-socket P2P синхронизация | Race conditions, дюпы, хаос состояний | Запрещена явно; только C++ authoritative |
| MP-режимы vanilla (DM, TDM) | Нет ALife, нет SP-режима | Отдельный game_sv_coop с ALife bridge |
| Lockstep детерминизм | Требует точной детерминированности всей X-Ray | Отклонён; server-authoritative snapshot |
| Полный переписывание сети | Огромный объём; сломает всё | Итеративный approach; reuse транспорта |

Предлагаемая архитектура избегает всех основных ловушек и выбирает правильный баланс между реализуемостью и корректностью.
